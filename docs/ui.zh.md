## 0. 产品对界面的真实要求

以下每个决定都源于关于 duang 的五条事实，而不是别的产品怎么做。

1. **用户是已经有 agent 在替别人干活的开发者**，不是尝鲜助手的消费者。
2. **本地这一半的存在理由是让你能接管。** README 原话：部署的 agent 出问题时，你"打开同一个聊天，读完整的工具轨迹，然后接管"。所以界面的首要任务是**审阅与干预**，不是陪伴。
3. **对话两侧极度不对称。** 你打的字短而稀疏：一个任务、一次纠正、一次停止。agent 产出的东西长、结构化，而且是你要扫读的：命令、输出、diff、报告。
4. **工作在后台并行、长时间运行。** 你回来查看的次数不亚于盯着看的次数，你需要看到几条会话里**哪条还活着**。
5. **transcript 就是工作记录。** 后续几周会加只读的工作区面板和云端活动收件箱，但没有任何东西会把 agent 的工作细节移出 transcript。

两条推论先说在前面：任何把 agent 输出**切碎**的做法（气泡、逐段卡片、装饰）与事实 3 和 5 冲突；任何为了列表整洁而**藏起并行工作**的做法与事实 4 冲突。

本文写于 Week 1 验收走查之后——那次走查里每个单独的信号都是真话，整体读起来却很糟。修法在这里，而不是再打一轮补丁（[#41](https://github.com/fastagent-sh/duang/issues/41)、[#42](https://github.com/fastagent-sh/duang/issues/42)）。

## 1. 三条原则

**agent 是联系人，会话是话题。** 默认视图是一份名册：你和谁共事、他们最近说了什么。一个 agent 下的多条会话是真实存在的，永远不会被隐藏，只是默认折叠。

**玻璃只属于导航层，绝不用于内容层。** 侧栏是毛玻璃材质，transcript 是实色。这是 macOS 26 自己的规则，也是长文本可读的前提。

**只在状态会让人付出代价时才说它。** 不是每个状态都值得一个指示器。详见 §9。

## 2. 参考对象，以及各自取舍的理由

借用一个解法就是借用它的前提。下面每条都写明它在别处成立的前提，以及那个前提在我们这里成不成立。

- **Grok Bot**（桌面端及 xAI 的设计文章）——**取**：以 agent 而非聊天历史作为主对象；系统事件与结构化结果和对话共享一条时间线；用做减法而不是加控件来解决问题。
  **拒，并附理由**：*两侧气泡*——它的前提是重活在 Bot 自己的电脑面板里，transcript 承载的是简短汇报；我们是事实 5，transcript 就是工作本身。*头像演生命周期*——它的前提是一个 Bot 一条对话，加上一个有表情可动画的角色；我们是字母方块加并行会话，所以头像用安静的光环表达 agent 在场，由会话行说明哪条在跑。*Status / Preview / Takeover 三档*——它的前提是一台你只能隔屏观看的机器；我们的文件就在本地磁盘，而且已经在用户的编辑器里打开了。*置顶与隐藏*——它的前提是多达 50 个 Bot 的名册；我们是你实际拥有的那几个 agent。
- **Claude Code 桌面端**——并行会话保持可见、可按状态过滤，因为并行工作对编码 agent 是常态。与我们的事实 4 前提相同。
- **Telegram**（tdesktop、macOS 与 Web 三端均开源，所以下面是**实测值**而非印象）——联系人行的节奏，以及两个值得直接照抄的技巧：
  - *行几何*。`dialogs.style`：行高 62px、内边距 10/8、头像 46px、名字 x=68 y=10、预览 x=68 y=34、未读徽章高 19px（12px 粗体）、日期 13px。真正重要的是关系：头像约为行高的 ¾，文字缩进 = 头像缩进 + 头像 + 12。§3 保留这个关系，但按工具的密度缩小，而不是照抄数值。
  - *头像配色*。`empty_userpic.cpp` 从八个固定颜色里按 `order[id % 7]` 取色，`order = [0, 7, 4, 1, 6, 3, 5]`——一张**刻意打乱**的表，让相邻 id 不会拿到相近色相。我们取这个打乱法，不取那套颜色：Telegram 的色块是中性界面上的高饱和马卡龙，而我们的旁边就是紫罗兰强调色，所以必须低彩度。
  - *Token 命名法*。`colors.palette` 把每个角色定义成一整套——`windowBg`、`windowBgOver`、`windowBgRipple`、`windowFg`、`windowSubTextFg`、`windowBgActive`、`windowFgActive`——而不是让组件自己去推悬停和激活色。§4 采纳这条纪律。
  **拒**：一个联系人只有一条线程的假设；行按下时的 ripple（那是 Material 的手势，macOS 应用不做）；以及按未读优先排序列表——agent 的列表该按"现在正在发生什么"排。
- **Carbon、HPE 设计体系、WCAG 1.4.1**——§9 的状态规则。
- **macOS 26**——玻璃只在导航层、侧栏延伸到窗口边缘、用原生材质而不是模拟。

## 3. 结构

两栏。后续几周会加第三栏和两个侧栏元素，现在先留好位置，届时无需重排。

```
┌ 侧栏 320（玻璃） ──────────────┬ 会话 ───────────────────────┬ (week 2) ┐
│ duang·              ⌘K    ＋   │  标题        模型 ⌄     ⏹  │  文件     │
│ [ local | cloud ]   (week 3)   │                            │  diff     │
│ ◎ Activity          (week 4)   │  回合                      │  设置     │
│ ┌────────────────────────────┐ │                            │          │
│ │ AM  amazonseo.ai       2m  │ │                            │          │
│ │     reading messages/es…   │ │                            │          │
│ │   • fixing the i18n check  │ │                            │          │
│ │     working                │ │                            │          │
│ │   ⌄ 2 more                 │ │                            │          │
│ └────────────────────────────┘ ├────────────────────────────┤          │
│   EX  existing-agent     1h    │  输入框                    │          │
│       你好，我是…              │                            │          │
└────────────────────────────────┴────────────────────────────┴──────────┘
```

**侧栏的行是 agent，不是会话**——一个 agent 一行。只有一条会话的 agent，看起来就只是一个联系人行。

几何按 Telegram 的比例、工具的密度：agent 行高 56，头像 40（圆角方块，同色相的双端渐变）——平涂的色块看起来像印上去的，渐变正是 Telegram 列表显得有生气的主要原因。当前会话是实心强调色行而不是淡色底，这是同一个列表的另一个手法：选中是"回应"，不是"打阴影"。第二行是工作目录而不是消息预览：目录才是 agent 的身份标识，而会话本来就列在它正下方。会话行高 32、无头像，缩进在所属 agent 之下。

**"打开某个 agent"和"看它有哪些会话"是两个问题，所以是两个控件。** 点击行打开 agent——这已经足以把它最近那条会话摆到屏幕上；再点一次当前所在的 agent 才列出它的会话，再点一次收起。没有任何东西会自己展开：打开 agent 已经回答了"我上次在这儿做什么"，在此之上再摊开名册，是在回答没人问的问题。行尾的箭头对任意 agent 都能做同一件事，这正是"点击行"表达不了的部分——第二个 agent 的会话就是这样在不离开当前会话的情况下出现的。可以同时展开任意多个 agent，收起其中一个也不会关闭你正在读的会话。哪些行是展开的属于视图偏好：只存在侧栏里，不跨启动记忆。

展开一个没有打开的 agent 会加载它的会话，这会像打开它一样启动那个 agent 的 runtime——会话列表归 FastAgent 所有，duang 不会自己再存一份"会话在哪里"。

选中一律用强调色，绝不用灰——灰是"指针停在上面"的样子。打开的 agent 是实心填充的那一行，当前显示的会话在它下面用淡色调：这一列先标出"你在哪个组里工作"，再标出"组里的哪个话题"。视觉重量跟随列表的层级，而不是被选中对象的大小。

**一整条平铺列表，不给每个 agent 套卡片。** 整宽的行、从文字位置起始的发丝分隔线、当前会话整行填充：Telegram、微信、Codex 画名册都是这样，理由在列表里有两个 agent 时就会显现——每项一张卡片会让这一列变成一摞面板，打开的那个显得格外厚重。会话行单行、缩进对齐 agent 的文字，相对时间跟在行尾、悬停时被 `…` 替换，这样话题在视觉重量上明显低于拥有它的 agent。`…` 打开这一行的菜单，而不是直接给出它最具破坏性的那个操作：一行只有一个下手的地方，而且和右键、Shift+F10 唤起的是同一个菜单。

**展开的 agent 会列出它的会话**，包括正在运行的和存有未发送文字的，因为事实 4 决定了"现在什么还活着"正是侧栏存在的理由。只有打开的那个 agent 会标出哪条在运行、哪条有草稿；其他 agent 的列表就是它的历史，它正在进行的工作体现在自己那一行上——呼吸光环加 `working` 一词。

读不出列表时，原因写在那个 agent 自己的行上，也只写在那里：展开从不改变主面板对这个 agent 的判断，因此折叠再展开你正在读的那个 agent，不会把窗口变成"这个 agent 坏了"。"这个 agent 没有会话"和"它的 runtime 起不来"不是同一个答案；而且这个失败属于被展开的那个 agent，绝不落到你正在读的 transcript 里。

tier-1 的状态同样以文字进入侧栏：`broken`、`needs a model`、`no agent yet` 都写在那个 agent 的行上——单独一个色点等于让颜色承担表意，只能靠 tooltip 读出来。存有未发送文字的会话在同一位置写 `unsent`，因为那也是没做完的工作。

在 transcript 里，被拒绝的请求会与 main 原话并列画出 `refused` 一词，原话逐字保留。语气承载两个词的区别：什么都没运行，所以那段文字仍然属于用户，可以继续改。

**在场状态分两层表达，因为侧栏要回答两个问题。** 头像承载 agent 自身的在场：只要它有任一会话在工作，头像外圈就有一道缓慢呼吸的 accent 光环，折叠与否都可见。agent 行用文字复述：`working`，多条时 `2 working`。会话行承载"是哪一条"：具体会话上的脉冲点加状态词。

折叠时信息已完整（光环 + 汇总词），展开后细化到具体会话。光环从不是唯一线索，颜色也就从不单独承担表意（§9）。

头像**不做的事**是表演。那些让头像演绎生命周期（思考、等待、庆祝）的产品，前提是一个 agent 一条对话、有一个可动画的表情角色、以及用户与它的消费级关系。我们的头像是代表一个目录的两个字母——呼吸光环是在场感，表演就是戏服。

**面板浮在窗口画布上。** 侧栏是从窗口边缘内缩的圆角卡片，而不是顶满边缘的一列；会话头部是浮在 transcript 之上的半透明条，而不是把页面切成两半的通栏。这是 Telegram 桌面端的构图，它的前提在这里成立：悬浮的外壳让底下的内容保持连续。不能照搬的是把 transcript 本身放到装饰性画布上——他们是气泡压在壁纸上，我们是必须保持可读的文档——所以 transcript 不透明，只有外壳浮动，并且 transcript 顶部留出让位空间，重要内容不会藏在头部下面。

按到来顺序预留：侧栏头部的 `local | cloud` 分段控件（Week 3）、名册上方固定的 **Activity** 行（Week 4）、以及右侧面板（Week 2，文件树、diff、发现到的设置）。那个面板是**阅读器**：文件就在本机、也已经在用户的编辑器里打开，duang 展示它们然后让开，而不是再建一个工作台。

侧栏不提供移除 agent。放在行上时它紧挨着折叠箭头，手一滑就移除了一个 agent；停在列底的链接又不属于任何具体对象。移除留在"解释问题的那块面板"里——agent 损坏、或目录里还没有 agent 的那两种情况——直到我们有一个可以安放它的菜单。

**不包含**：置顶、隐藏、归档、分组。那些属于五十个 agent 的名册；对五个的列表而言，它们是凭空制造的管理负担。等真有列表读不动了再加其中一个。

**模型 chip 和它的选择器参照 Codex，按 duang 自己的条件做。** chip 上提供方用淡色、id 用正常色，后面跟着推理强度（`openai/gpt-5 Minimal`）；提供方不能省，因为 `openai/` 和 `openai-codex/` 的 id 相同，付费方式却不同。它打开一个对齐在 chip 右缘的浮层：一行搜索、按提供方分组的模型（只显示 id，用系统字体而不是等宽，14px）、以及推理强度。强度是一个原生 radio 组，画成一条带刻度的轨道，每档一个刻度，所以方向键和朗读都是平台的；刻度就是运行时给出的档位，而且档位属于会话，所以还没开始的会话会直接说明。轨道立刻显示所选的档位。点击立刻写入；方向键要等停顿（150ms）或选择器关闭才写入：方向键划过四档，否则会往会话记录里写四个档位；被拒绝时轨道回到运行时所在的档位。选择总是写给做出选择的那个会话，不管等了多久：期间切到别的会话，先把等待中的写出去，而不是挪到新会话上。列表最多显示 60 行，并说明还有多少没显示，因为排在限制之后的提供方连标题都不会出现。FastAgent 没有给出模型的友好名称，从 id 猜一个名字，就是给运行时并不这么叫的模型起了名字，所以列表显示 id。选择器里不放的：凭据文件路径（用户无法据此做任何事）和"管理提供方"链接（设置在侧栏里；空列表仍保留唯一的 **Connect a provider**）。

**标题栏分成两块**：你正在看的东西（头像、agent 和对话、目录、`working`、套餐和上下文用量、`queued`）是一块胶囊，对话上唯一的操作（会话列表）是它旁边的一个圆盘，和 Telegram 把聊天信息与通话、搜索、菜单分开的做法一样。标题栏走满窗格宽度：它是外壳，限制在阅读栏里会读成页面中间的一张卡片。输入框则不是：它在阅读栏里，附件和语音/发送两个圆盘正好在文字的两个边缘上，因为视线是从最后一行直接落到输入框的，输入框比文字宽就成了一次跳跃。圆盘是孤零零一个，因为对话上现在没有别的操作：新建对话在侧栏里，而一个里面什么都没有的菜单只是摆设。

**输入框是 Telegram 那样的单行**：左边是附件按钮，中间是输入框，右边一个圆按钮，它就是"下一步动作"：输入框为空时是语音，有文字时是发送，运行中是停止。属于下一条消息、而不是属于应用的设置，放在输入框里面靠右的位置（Telegram 放表情的地方），所以模型芯片在这里。输入框是 40px 的胶囊，随行数增长变成圆角矩形（最多八行），按钮始终和最后一行对齐。附件和语音都显示出来但处于禁用并带着原因：duang 里还没有附件的通路，而且发出去的图片不会回到 transcript，因为 FastAgent 的 `user_message` 不包含图片。

窗口默认 1280 × 840——侧栏加阅读栏及其内边距，让全新安装第一眼就是 transcript 被设计时的宽度——并且重开时回到上次的位置和大小。尺寸与位置属于导航记忆，和"上次选中的 agent"同类：尽力保存，读不出来就当首次启动；如果上次所在的显示器已经拔掉，窗口回到还连着的那块屏上。

## 4. 色彩

oklch，双模式，跟随系统。中性色阶取自 Telegram macOS 深色主题的实测值——台阶小、几乎无彩度——但改了一处关系：transcript 所在的画布是最暗的一层，所有面板浮在它之上，这样面板读起来是"抬起来的"而不是"挖下去的"。浅色模式不是把这套镜像过来，而是遵循 macOS 惯例——内容白、侧栏灰，和 Finder、邮件、微信一致——因为白侧栏配灰内容读起来像窗口被翻了个面。色阶保留一丝强调色色相（285），让紫罗兰属于这套体系，而不是贴在一个灰色应用上。

| `warning` | `oklch(0.79 0.15 65)` | `oklch(0.58 0.15 60)` | 缺模型、尚无 agent |
| `danger` | `oklch(0.68 0.17 25)` | `oklch(0.52 0.19 25)` | 破损、失败、危险操作 |

强调色当文字和当表面不能是同一个值。作为文字它要压在页面上，所以深色模式里必须偏亮；作为白字下的填充它必须偏暗，否则选中的 agent 会成为屏幕上最亮的东西。因此两个填充色**不随主题变化**：两种模式共用一个选中紫，就像 macOS 和 Telegram 共用一个选中蓝。L 0.52 上的白字约 4.2:1，和 Telegram 选中行持平。

每个可交互角色都成套定义，而不是在调用处临时算——Telegram 的调色板就是这么做的，这也是他们的主题始终自洽的原因：`bg` / `bg-over` / `bg-active`、`text` / `muted` / `fill-fg`。组件只挑角色，从不自己计算悬停色。

头像色块走七种固定低彩度色相，按 `ORDER[hash % 7]` 选取，`ORDER = [0, 4, 1, 6, 3, 5, 2]`。这张打乱表来自 Telegram，作用是让先后注册的 agent 不会长得一样。

## 5. 字体

```css
--font-sans: system-ui, "PingFang SC", sans-serif;
--font-mono: "Maple Mono NF CN", "JetBrains Mono", "SF Mono", ui-monospace, "PingFang SC", monospace;
--font-prose: "Prose", "PingFang SC", sans-serif;
--font-avatar: "Avatar", "Prose", "PingFang SC", sans-serif;
```

控件、导航和工具追踪用系统字面，配系统自己的 CJK 字面。字体栈以 `system-ui` 开头，它是 Chromium 唯一会映射到 SF 的名字：`-apple-system` 是 Safari 的写法，"SF Pro Text" 系统不会按名字给出；以前的字体栈开头是这两个，于是落到苹方，界面里的英文全用苹方画，连字符是 0.6em，SF 的是 0.43em。这是一个隐藏标题栏的原生窗口，界面外壳里摆一个 web 字体会读成网页而不是应用。对话本身是例外（见下）。**不要**把 CJK 塞进等宽族；在代码语境里让它回退到 PingFang SC，也不要把它压变形。Maple Mono 是全应用唯一的等宽字体，工具追踪和回答都用它，回答里提到的命令和实际运行的命令长得一样。句子里的行内代码小一档、常规字重、铺在纸面更深一层的底色上、不加描边：是句中被标记的词，不是贴上去的标签，也不会在加粗句里变成一块深色条。

**对话有自己的声音 `Prose`**：一个名字下的两个打包圆体，英文 Nunito，中文资源圆体（Resource Han Rounded）。用系统无衬线时，回答和其他聊天应用分不出来。Maple Mono CN 的中文就取自资源圆体，所以回答和它引用的代码共用同一套中文字形；单独用它，是因为 Maple 的中文放在 1.2em 的格子里以便终端对齐，放进段落会把每句话撑散。英文也试过直接用 Maple Mono，读起来吃力：等宽的一行宽出三分之一，也没有词形。中文字体裁剪到 GB2312（每个字重 1.1 MB），更生僻的字回退到苹方。两个字体都是 OFL 许可，许可文件放在 `src/renderer/fonts/`。Nunito 放大 10%（`size-adjust`）：它的 x 高度是 0.48em，资源圆体是 0.54，同样的标称字号下英文会比旁边的中文小一档。每个英文字体和对应的中文字体声明完全相同的字重和样式：Chromium 先按描述符选定一组字体，再看 `unicode-range`；当 Nunito 声明成 `200 1000`、中文是 `400` 和 `600` 时，Nunito 从未加载，英文静默回退到了苹方。smoke 测试会检查英文字体确实加载。斜体和粗斜体各有自己的字面（英文 400 和 600，中文 400 和 700），所以强调不会丢字重；中文没有斜体，浏览器也不会把声明为斜体的字面再倾斜，所以中文在强调里保持直立。

按归属划分，不按位置：**人写下的文字无论在哪里被引用，都用 `Prose`**，同一句话从气泡到顶栏不会换字体。这包括侧栏每行的预览、agent 的名字（行里、重命名输入框和顶栏）、顶栏的对话标题、对话列表的各行和重命名它们的输入框，字号各按原位置。名字也是这样的文字：它是用户起的，而 agent 是一位联系人。应用自己说的话都留在系统字体：时间、徽章、错误、控件和工具追踪。

**头像的首字母用 `Avatar`**：Fredoka 600，只裁剪拉丁部分（16 KB，OFL，许可文件在 `src/renderer/fonts/`）。试过的字体里（Nunito、Baloo 2、Quicksand、Sniglet、Grandstander、Lilita One、Chewy、Bubblegum Sans、Varela Round、Comfortaa）它最圆最有弹性，在 30px 的顶栏尺寸下仍然认得清，而 Sniglet 的字形在这个尺寸下 `AM`、`WR` 已经糊在一起。头像只有两个字母，不需要和回答用同一个字体。中文名不在 Fredoka 里，回退到 Prose 的中文字体。smoke 测试会检查这个字体确实加载。

**中文是一等公民，而 CSS 看不见它。** CJK 字形填满字面框，同字号下比拉丁文需要更大的行高。`:lang(zh)` 是表达这件事的自然写法，但在这里它不工作：文档是 `lang="en"`，而且没有任何地方把一条中文消息标记为中文，所以那条规则一次都没有生效过。只有逐条消息做文种识别才能做到，而那是为 0.05 的差别买来的第二份 transcript 事实来源。所以正文只用**一个**行高 1.7：对中文正好，对英文略松，而这里是文档列不是密集列表。它只写在一处 `.md, .bubble`，输入框也穿同一件，这样长消息发出去时不会重排。

同一行里的中文和英文、数字之间，由 `body` 上的 `text-autospace` 自动加六分之一个空格：模型输出有时打了空格有时没打，浏览器只在缺的地方补。代码、路径和工具输出不加：这个间距会把含中文的行推离 Maple 的 2:1 网格，列就对不齐了。全角标点保留 Chromium 默认的挤压（`text-spacing-trim: normal`）；把所有标点都压成半宽是日文习惯，不是中文的。正文用 `text-wrap: pretty` 换行，段落不会以“单。”这样的孤字结尾。

导航和工具追踪保持紧凑；正文和标题留更多空间，这样结果能被扫读，又不会把追踪变成第二份文档：

| 用途 | 字号 / 行高 / 字重 |
|---|---|
| agent 名、`New conversation` 标题 | 13.5 / 1.4 / 600 |
| 回答标题 | 22 / 19 / 17（h1–h3），更低级 15 / 1.4 / 600 |
| 对话正文、发出的消息、输入框 | 15 / 1.7 / 400 |
| 回答里的表格 | 14 / 1.6 / 400，表头 600 次要色、浅色色带 |
| 侧栏行 | 13 / 1.7 / 400 |
| 工具行、thinking、模型列表、卡片正文 | 12 / 1.5 / 400 |
| 代码、路径、工具输出 | 12.5 / 1.625 / 400，等宽 |
| 行内代码 | 所在行的 0.875em（至少 11）/ 400，等宽 |
| 徽章、时间、标签 | 11 / 1 / 400–500 |

等宽比旁边的无衬线高半档是故意的：它的 x 高度更小，同样的标称字号读起来更小。没有任何地方用 10 或 11.5——半个像素的台阶看不见，唯一的作用是让两个本该一致的东西不一致。

强调用字重，永不用色相。正文文字从不着色。

## 6. 图标

Phosphor，Bold 粗细，通过 `IconContext` 全局设定一次，尺寸 11–16px。用 Bold 而不是 Regular，因为 Regular 在这个尺寸下是发丝线：挨着 13px/600 的文字时它比字更细更灰，这正是"界面像编译器画出来的"的主要来源。Bold 大致等于 SF Symbols 的 semibold，也就是 macOS 自己在这个字号旁边用的粗细。因此强调靠颜色而不是粗细——运行中的工具图标取强调色，失败的取危险色。每个图标都带标签或 `aria-label`；纯图标控件只存在于符号通用之处（发送、停止、关闭）。

## 6b. 控件

按钮只有四种，没有第五种。`primary` 是填充强调色，一屏最多一个——"此处该做的那件事"。`secondary` 是描边的备选项。`ghost` 用于行内、标题栏和输入框里的操作。`danger` 用于删除和移除，平时安静、只在指针落上去时才变红，因为这些按钮长期停在界面上。`loud` 把某一种按钮从着色改为填充，只服务于唯一必须一眼找到的控件：Stop。

三种尺寸：行内和密集工具条用 28，独立站立用 32，40 是圆形，只给输入框的图标按钮用。纯图标按钮是同高的正方形（40 时是圆形），且只在符号本身通用时使用（§6）。字号也由尺寸决定（28 是 11px，其余是 12px）：Tailwind 的工具类优先级相同，调用点传入的字号最终由生成样式表里的顺序决定，而不是由意图决定。调用点能传的东西不允许和组件矛盾；需要变化的，做成属性。

**禁用的控件必须说明原因。** `disabled` 接收的是原因文本而不是布尔值，因此没有办法悄悄把一个控件变灰：它降到 40% 不透明度、保持原形状、并带着原因。比如"Stop the turn to change the model""Voice input is not available yet"。它用 `aria-disabled` 而不是原生属性来表示禁用，并保持可聚焦——原生禁用的按钮键盘无法到达，而到不了的原因等于没有原因（WAI-ARIA APG）。点击和键盘激活由组件本身丢弃。

`npm run shots` 会把所有控件的总览表在深浅两种模式下写到 `out/shots/components-{dark,light}.png`，用的是和应用同一份构建；把窗口加载到 `#gallery` 也能打开它。"我们到底有哪些组件"这个问题由此靠看来回答，而不是靠读文档。表里每一段都用固定的 props 渲染应用自己的组件，组件改了这里就跟着变；需要实时状态的界面（两个列表、标题栏、输入框）由运行中应用的截图覆盖。hash 只在加载时读一次、不是实时开关，所以回答里出现 `#gallery` 链接也不会把正在运行的应用卸载掉。

状态一律是徽章：一个色点或图标，随后是文字，用该状态的颜色——绝不只靠颜色表达（§11）；只有"仍在发生"的状态才带脉冲。

浮层共用同一种表面——`surface`、圆角 14、一条发丝描边、全应用唯一的一层阴影——尽管模型列表是会夺取焦点的模态对话框，而 `/` 补全列表刻意不夺焦点。两者是同一种表面和同一种行（14px，当前项用中性色高亮，命令的说明和来源在旁边更淡），模型选择器打开时，`/` 列表会让开。

## 7. 间距、圆角、层次

- 间距阶梯：4、8、12、16、24、32。
- 圆角：6（徽章、小控件）、10（卡片、气泡、输入框）、14（浮层、对话框）。气泡尾角收到 4——正是这个不对称让它读起来像说话。
- 层次靠明度差加一条细线，不用阴影。只有浮层允许一层柔和阴影。
- 侧栏与会话区之间不画分隔线：材质变化本身就是分隔。

## 8. 消息呈现

transcript 是一份两侧极不对等的工作记录（事实 3 和 5），所以两侧刻意画得不一样。

**你发出的是气泡。** 右对齐、`accent-weak`、最大宽 560。你的回合短而稀疏，它们的职责是回滚时好找：*我当时要求了什么，又在哪里改的口？* 气泡适合做锚点，正因为它小而醒目。

**agent 产出的是文档。** 左对齐、无气泡、完整 markdown，放在一条阅读栏里：随窗格宽度伸展，最大 840，居中；正文、列表、代码、表格和输入框共用这条栏，所有边缘对齐，视线从文字直接落到输入框。15px 下一行约 56 个汉字；920 时约 61 个，眼睛回到下一行开头会迷路；768（51 个）用过一段时间，读起来偏窄。标题栏是唯一不进这条栏的。transcript 两侧都预留滚动条轨道，这样它的栏和输入框的栏中心一致。你写的、你发出的和 agent 回答的是同一个声音：15px、行高 1.7，比导航高一档、比工具追踪高两档。transcript 是事后要细读的报告，所以用阅读字号；产生它的过程留在 12，读起来是旁注。加粗用 600 而不是浏览器默认的 700。间距用来分组而不是一律分开，取 §7 的阶梯：两个段落之间 12，段落和它引出的列表只隔 4；标题上方 24、下方 8；代码块、表格和引用 16，分隔线 24。Streamdown 自带的 `space-y-4` 让每一对都用同一个间距，所有块等距分开，什么都读不出归属。表格是文档的一部分：完整高度而不是内部滚动，无边框，表头是和代码块同一家族的浅色色带，行间细线。它写的是命令、输出、计划、diff 和报告；把这些裹进对话气泡，等于把需要扫读的记录切碎，还白白让出内容最需要的宽度。两侧都用气泡的产品，把重活放在了别处——一个独立的工作区面板——所以留在 transcript 里的确实只是闲聊。我们的 transcript 就是工作。

其余都由这两条推出：

- **一段连续的工作是一行。** 连续的工具调用与 thinking 合成一个工作块，只说是哪类工作：`thought 6s, read 4 files, searched once, ran 1 command`。块上不单独标出失败的调用：agent 会自己读失败并继续，用户对它无事可做，整体是否失败由 run 的结果说明；展开后那条调用仍写着 `failed`。没跑完的调用不同，摘要里会写出来：`ran 2 commands, 1 stopped`。agent 没读到它的结果，run 也没有继续；重新打开的会话历史里没有 `run stopped` 那一行，摘要是唯一能看出工作被中断的地方。展开后是逐条调用，挂在一条细线下。运行中它保持折叠，因为 run 的实时状态行已经说明当前这一步；例外是：只有一条时被人点开过的调用，在下一条调用把它并进块后，整个块保持展开，不在读的人眼前收起。只有一条调用时保留它自己的行；它正是当前步骤时，下方实时状态行只写步骤词，不重复它在处理的内容。
- **run 的末尾说明它正在做什么。** 整个 run 期间 transcript 以一行朴素的文字结束：一个弹跳的强调色圆点、当前步骤（`thinking`、`reading …/src/a.ts`、`running npm test`、`answering`、`compacting`，run 被报告前是 `starting`），以及本窗口看到 run 开始以来的耗时；打开时已在运行的 run 不显示时长。
- **工具调用折叠时是一行，展开才变成卡片**：折叠时是图标、工具名、命令，状态紧跟在命令后面，而不是甩到最右端、脱离它的主语；没有底色也没有边框，和旁边的 `thinking` 行同一个分量。给折叠态加框两个方向都错：铺满整列是一条灰板，缩到文字宽又像一颗掉进正文里的按钮。表面只在有输出要托住时才出现。展开后卡片显示参数（标签加值，而不是传输用的 JSON）与结果（从 MCP content 信封里取出来）；输出满十二行或满 1500 个字符就折叠（哪个先到按哪个算；一行压缩过的 JSON 没有行数上限），折叠成横跨卡片的一行页脚，不自带滚动区。参数值按同样的上限折叠，因为 `write` 的参数里带着它要写的整个文件。无法拆开的结构保留原始 JSON：看不见的结果比难看的结果更糟。状态后面是工具的运行时长：运行中每秒刷新一次，所以只显示整数秒；结束后用 pi 的格式（`3.2s`、`2m 5s`）。只有本窗口看着运行的调用才有时长：历史只记录调用发出和结果写入的时刻，不是工具跑了多久，所以重新打开的调用不显示时长。这个视图收不到 run 的消息时，计时随之停止。
- **thinking** 折叠成一行 `thinking · 3s`，后面跟着当前这一行，展开为引用块。
- **系统事件是居中的一行灰字**：模型已切换、运行已停止、发送被拒。它们是关于会话的事实，不是任何人说的话。
- **消息放在运行时报告它进入对话的位置**：发出后，它先以半透明的样子停在实时输出下方，标注 `sending`；运行时把它列入 `pending.steering` 时标注 `queued`。等 FastAgent 报告它进入对话（`user_message`），它才落进 transcript：steer 要到 run 的下一个回合边界才会被读到，发送时就放进去，会让它出现在模型还没读到它时写下的输出上方。显示的队列归运行时所有，所以重新加载前排队的、或别的客户端发的 steer 也会显示。run 结束时仍在队列里的消息已被丢弃，它回到草稿，不会被显示成已送达；重新加载前打的 steer 也一样，因为它的文字已经没有别处保存。扩展命令如果只做事、不往对话里发任何消息，会留下一行 `ran /go X`。消息按文本对应到本窗口发出的那条；斜杠命令对应最早一条等待中的命令，因为运行时报告的是展开后的文字。别处发来的消息如果排在我们的命令前面，可能占掉它的位置。
- **被 steer 的消息**保留气泡，并在前缘加一道 accent 竖线和标签 `joined the run`：它进入的 run 之前已经有一条用户消息。事后再没有别的东西能把它和"开启一个回合"的消息区分开。*仅存在于实时视图*：FastAgent 的会话条目只存文字、不表达"当时有 run 在跑"，所以重开会话后气泡还在、标签没了。要推导出它就得自己再存一份 transcript，而这个应用不那么做；让它持久化的请求提在上游 [fastagent#595](https://github.com/fastagent-sh/fastagent/issues/595)。
- **会话要么有名字，要么借用第一条消息。** 标签归 FastAgent 所有（`update({ name })`），在没人设置它之前，行会退回到开头那句话——这正是"话题变了标题不变"的原因。重命名就在行内发生，入口按 macOS 的习惯给：行的右键菜单里有 `Rename…`，双击行也直接进入编辑——单击已经是"打开"，所以双击是空着的，Notes 的文件夹和 Safari 的书签就是这么做的。Enter 保存、Escape 放弃，空名不算重命名。菜单用原生菜单，因此看起来像系统的而不是我们自己的浮层；Chromium 对 Shift+F10 和 Menu 键同样会唤起它，那就是键盘路径。不用 F2——那是 Windows 的习惯。duang 也不会让模型替你起名：那会花掉一次没人要求的请求。
- **回到当前回合的入口。** 向上滚动会让视图停止跟随尾部，而那一刻正是输入框上方出现"回到最新"按钮的时刻。它只在那个条件成立时存在，所以贴底的 transcript 上什么多余的东西都没有。
- **结束的回答尾部写明它落地的时间，并给出复制的入口**，此外什么都不放。运行很久、常常事后才读，所以时间是记录的一部分；复制按钮在悬停时出现。只有结束一轮的那段话才带这一行：之后还要继续干活的话是步骤之间的旁白，每段下面都挂一个时间，等于在每一步之间塞了一行元数据。评分在这里无处可送，分支和编辑也不是功能，所以别的客户端塞满图标的那一行，我们只留两样。
- **流式输出**尾随一个块状光标 `▍`，它不用转圈就表示"还在写"，结算时消失。
- **间距由"前后是什么"决定，而不是一个常数。** 用户发出的内容之上 32、之下 24，agent 的话与它的工作之间 12，两条旁白之间 **8**——工具调用、thinking 行、系统提示、运行状态行都算旁白。它们是同一件事的单行，给 `bash` / `thinking` / `bash` 段落级的间距，会把工作日志读成一张稀疏列表；话与工作之间用 24 时，每条工具行都悬在自己的一段空白里。追踪里的单行（工作摘要、工具调用、thinking、运行状态）一律 28 高，节奏一致。最后一行到输入框之间留 48：运行期间 transcript 一直吸在底部，所以那段间距正是最新一行落脚的位置，16 的时候它会压在输入框边缘、被渐隐盖住一半。
- **日期分隔**：会话跨天处插入一行居中灰字。在这里"读昨天那次运行"是常态，没有分隔的话，一条后台会话读起来像是一口气发生的。Telegram 从第一天就有这个，理由相同。

## 9. 状态

三档，按"这件事需不需要你做点什么"划分。Carbon 明确指出：不需要用户行动的指示器应当改为普通文本或干脆不显示；HPE 的经验法则是一个状态至少要携带颜色、图标、形状、文字中的三项。事实 4 追加了我们自己的要求：人经常不在场，所以"它还在干活吗"必须能从侧栏直接读到，不用打开任何东西。

| 档 | 状态 | 如何呈现 |
|---|---|---|
| **需要决策** | broken、needs a model、no agent yet、failed、stopped、refused | 永远有文字，加图标或形状。颜色是第三重信号，绝不单独出现。 |
| **只需安心** | working、thinking、running | 头像上的呼吸光环、会话行上的脉冲点与状态词、transcript 末尾一行实时状态：当前步骤加 run 的耗时。 |
| **无事可做** | ready、done（已看过） | 什么都不显示。成功的工具卡不带任何徽章——一条 trace 里十张卡有九张写着 `done`，真正失败的那张就是这样被淹没的。 |

全局一套词，同一状况不许在这里叫 `working`、在那里叫 `running`：

`working` · `thinking` · `running` · `reading` · `searching` · `editing` · `fetching` · `answering` · `compacting` · `starting` · `done` · `failed` · `stopped` · `refused` · `unsent` · `needs a model` · `no agent yet` · `broken`

`unsent` 是正式进入词表，而不是词表的例外：存有没人发出去的文字的会话属于未完成的工作，而词表里没有别的词能表达这一点。`done` 仍留在词表里，是为了这个词本身——当某处必须给"完成的工具"一个称呼时（比如 tooltip）用它——但第三档规定它不出现在屏幕上。

**你不在场时发生的结果，属于需要决策，而不是安抚。** 运行往往很久，事实 4 说你会离开再回来，所以一次在你读别处时结束的运行会留下标记：会话行用**实心药丸**写 `done` 或 `failed`、标题同时加粗，agent 行把它们汇总（`2 done`、`1 failed`，失败优先占据汇总位），并且总数落到 **Dock 角标**上——这样不用 duang 在最前面也能知道。最初做成淡色文字，实测连续几次都没被注意到；这是整个界面里唯一必须"隔着房间也看得见"的标记，所以采用 Telegram 的未读药丸，不用更安静的做法。打开那条会话就把标记花掉，和未读数被读掉一样——它存在的全部意义就是消失。你自己停掉的运行不留标记，因为你已经知道了。标记只存在内存里：它是关于"这个窗口的注意力"的事实，而 transcript 仍是唯一持久的记录。

这也是 `done` 能同时属于两档的原因：没看过时它是你该回来的理由，看过之后它就是无事可做的状态，于是安静下来。

`refused` 与 `failed` 刻意分开：被拒的发送从未运行，文字仍归你编辑；失败的运行已经跑过，副作用可能已经存在。

`stopped` 是新增的必需项：被你中断的工具目前显示 `failed`，那是把你的决定说成它的错误。

**在场状态分层，不重复。** 头像回答*这个 agent 是否在忙*（呼吸光环），agent 行用文字说出来（`working`、`2 working`），会话行回答*是哪一条*（脉冲点加状态词）。每一层提供上一层给不了的信息；彼此不重复，也没有一层只靠颜色。

## 10. 动效

一条缓动曲线 `cubic-bezier(0.2, 0, 0, 1)`，三个有名字的形状。这套词汇借自 Beautiful UI，借的是词汇不是组件：一小组动作被一致地使用才读成精致，一大组动作偶尔使用只会读成 demo。

| 形状 | 是什么 | 用在哪 |
|---|---|---|
| `enter` | 透明度加 6px 上移，180ms | transcript 里任何新到达的东西：消息、工具调用、实时状态行。history 不算——打开会话时已有的内容静止显示 |
| `pop` | 透明度加从 0.96 放大，160ms | 就地出现而非到达的东西：`回到最新` |
| `shimmer` | 一道高光扫过文字，2.4s 循环 | 正在干活：实时状态行的当前步骤、流式中的 `thinking` |
| `bounce` | 圆点起落、落地时压扁，900ms 循环 | 实时状态行的标记：duang 就是弹跳的声音 |

`shimmer` 取代了让标签透明度闪烁——那是一个界面能做的最廉价的事，而这里它一次会在屏幕上停留好几分钟。

折叠项靠生长打开。`interpolate-size: allow-keywords` 加上 `::details-content` 上的过渡，不需要任何 JavaScript 量高度就能动画到自动高度——这是跑在已知 Chromium 上的 Electron，这个特性直接可用。应用里的两种折叠项（工具调用和 thinking）都是从一行变成一块输出，而这一跳正是让 transcript 读起来像在自我重绘的原因。

悬停背景 100ms，浮层 120ms，在场状态 1.8s 呼吸——头像光环与会话脉冲点同步。**流式文字不做动画**：token 的到达本身就是动效，再叠过渡只会抖。`prefers-reduced-motion` 下全部退化为瞬时。

## 11. 可访问性

焦点环为 `2px accent`、偏移 2px，只在 `:focus-visible` 出现，且永不用于文本框（光标和容器已经表明了）。正文对比度在两种模式下都不低于 4.5:1。状态遵循 §9；没有任何状态只靠颜色。

**整个名册只占一个 Tab 停靠点**（WAI-ARIA APG）：Tab 进入它，方向键在里面移动。上下键把 agent 和它们的会话当作同一个列表来走，Home/End 跳到两端，Enter 打开键盘当前所在的那一项。键盘从"当前打开的东西"开始，之后停在你上次移动到的位置。

**行内控件是按键，不是 Tab 停靠点。** 每行都有折叠箭头和删除按钮，会让 Tab 把名册走三遍，所以由行本身代答：左右键展开/收起 agent，Delete 或 Backspace 删除键盘所在的那条会话（在 macOS 上主键盘那颗删除键是 Backspace，那才是用户真会按的一颗），并且两者都不会去删运行时还不认识的会话——那种行本来也没有删除按钮。`New conversation` 同理，是列表里的一行。删掉一行后焦点交给它的邻居，列表因此仍可继续导航。这些控件仍可点击、仍对辅助技术保留标签；它们失去的只是 Tab 顺序里的位置。

**transcript 是一个具名的可聚焦区域**，因此无需指针也能阅读和滚动——滚动容器一旦获得焦点，Chromium 就会把方向键交给它。

## 12. 品牌

产品名是 `duang`，**全场景小写**——仓库、文档、窗口、宣传。字标是名字本身，字重 600、字距 -0.01em，尾随一个强调色圆点：`duang·`。这个名字本身已经够活泼，排版不再加戏。

agent 头像是圆角方形而不是圆形——圆形是人，方形是程序，在一个以"agent 是联系人"为核心隐喻的产品里，这个区分是值钱的。头像显示名字前两个字母，底色由名字哈希落在八种低饱和色相之一。方块本身只承担身份；在场状态是它外面那道光环（§9），绝不改变方块本身，这样忙碌与空闲时它仍是同一个 agent。

## 13. 实施顺序

1. **Token 层**：两套色彩模式、字体栈、圆角与间距阶梯；把 `lucide-react` 换成 `@phosphor-icons/react`。不改结构，不改行为。
2. **组件层**：按钮（primary / secondary / ghost / danger，高度 28 与 32）、徽章、卡片、浮层、输入框。
3. **状态层**：统一词表、三档规则、新增 `stopped`、两层在场状态（头像光环与会话脉冲点）。
4. **侧栏**：rail 与会话列表合并为一栏 320 玻璃：agent 行、运行中与有草稿的会话永远列出、其余折叠。**这一步改导航结构**，smoke 里所有按标签定位控件的断言都要重新核对。
5. **transcript**：用户气泡、agent 的文档栏、工具卡片、居中系统事件、steer 竖线、流式光标。
6. **键盘**：roving tabindex、可聚焦的 transcript。

第 1–3、5–6 步不改行为，可以带着现有测试落地；第 4 步会改。
